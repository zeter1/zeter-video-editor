# Правила версионирования и ведения CHANGELOG.md

## Цель

История изменений должна отвечать на вопросы: **что изменилось, где, зачем, что почувствует пользователь, совместимы ли старые проекты, чем проверено**. Ведём записи на русском в корневом [CHANGELOG.md](../CHANGELOG.md), а не копируем туда автоматически commit-log. На каждое значимое изменение нужен отдельный осмысленный пункт.

Основание: [Keep a Changelog 1.1](https://keepachangelog.com/ru/1.1.0/) и [Semantic Versioning 2.0](https://semver.org/spec/v2.0.0.html). По специальному требованию этого проекта **не используем заголовок `Unreleased`**: работа в ветке целевой версии собирается в её датированном разделе. Статус `предварительная / не опубликована` пишем явно, чтобы не путать с публичным подписанным релизом.

## Обязательная инструкция для следующего диалога с ChatGPT / разработчиком

**Эту секцию читать заново при каждом продолжении разработки, даже если предыдущий чат недоступен.** Не определять актуальную версию по памяти, тексту пользователя, старому checkpoint или имени ветки: источник истины — текущий код и состояние GitHub.

### Шаг 1. Восстановить реальные факты

1. Изучить `AGENTS.md`, `PROJECT_STATUS.md`, этот файл и `CHANGELOG.md`; при наличии рабочего Google-документа прочесть его свежий checkpoint. Правила версий находятся именно в этом файле, а Google-документ служит дополнительным указателем на PR/CI и задачи.
2. Проверить фактические HEAD SHA `main` и рабочей ветки, существующие draft/open/merged PR, статусы **точно их коммитов** и последние GitHub Releases. Не считать draft PR частью `main`.
3. Прочитать `apps/desktop/package.json` и остальные перечисленные ниже манифесты. Выяснить, нужна ли новая версия или лишь новая запись в существующей версии. Не увеличивать номер по умолчанию при каждом коммите.
4. До начала реализации сформулировать изменение и предполагаемую категорию записи. При затрагивании пользовательских проектов или протокола отдельно проверить сохранение совместимости/нужные миграции.

### Шаг 2. Реализовать и описать каждое изменение

- Для **обычного PR** не менять номер приложения автоматически. Добавить в `CHANGELOG.md` текущей рабочей ветки отдельные подробные пункты с конкретными путями/функциями, поведением до/после, последствиями, совместимостью, ограничениями, тестами и ссылкой на PR, если номер известен. Новая функциональность и реальное исправление безопасности — отдельные пункты; изменение E2E-теста — не выдавать за новую функцию редактора.
- Для **новой сборочной версии** использовать только `node scripts/set-version.mjs X.Y.Z[-stage.n] --note "содержательное описание от 25 символов"`. Скрипт изменяет номер программы и добавляет датированный раздел. После него дописать подробные пользовательские/технические изменения и честный статус (`в разработке`, `кандидат`, `опубликована`).
- Не писать о функциональности из соседнего draft PR в журнал `main`, пока она реально не интегрирована. При слиянии нескольких веток сохранить все содержательные записи; устранить дубли и пересечения, проверить соответствие именно результирующему коду.
- Чистые refactoring/CI/test/docs изменения тоже описывать, если они важны для сопровождаемости, воспроизводимости, стабильности, безопасности или релизного процесса.

### Шаг 3. Проверить, отправить и зафиксировать для продолжения

1. Запустить `node scripts/check-version.mjs` и при готовящемся теге — `node scripts/check-version.mjs --tag vX.Y.Z[-stage.n]`; исправить расхождения, а не обходить проверку.
2. Выполнить относящиеся к изменению TypeScript/Vitest/Rust проверки и **exact-HEAD Windows CI**, включая реальный WebView2 E2E и упаковку NSIS там, где требуется. Записывать статус и SHA без предположений и не переносить успешность с предыдущего коммита.
3. Перед окончанием задачи сверить PR diff: в нём должны находиться и код, и соответствующие строки `CHANGELOG.md`, и документация при изменении правил. По завершении merge сверить фактический `main` с записью. Не делать merge, тег, установку или выпуск на основании одного лишь изменения номера.
4. В `PROJECT_STATUS.md` и Google checkpoint указывать: текущая версия **и статус**, названия/ссылки PR, branch/base/exact SHA, изменённые файлы, проверки (прошло/не прошло/не запускалось), риски и следующий шаг. Это позволяет следующему диалогу возобновить работу **без догадок**.

### Шаг 4. Если действительно готовится публичный релиз

- Только после отдельного решения о релизе, проверенного Windows CI, независимого review, ручного Windows QA, проверки Windows и updater signing, лицензий FFmpeg/AI и совместимости пользовательских проектов.
- Готовить подробные релизные заметки командой `node scripts/release-notes.mjs X.Y.Z --output release-notes.md`. Проверять, что в файл попала только фактически вошедшая версия, что она соответствует тегу, и что нет заявлений о неподписанных/непроверенных функциях.
- GitHub tag, Release, автообновление и дистрибутив **отдельные действия**, не происходят от изменения текста changelog или номера приложения.

## Единая схема номеров

- Номер **desktop-приложения** следует SemVer `MAJOR.MINOR.PATCH[-prerelease]`: например `0.1.0-alpha.1` — предварительная сборка; `0.1.0` — будущая стабильная версия, только после отдельного решения о выпуске. `alpha` → `beta` → `rc` — стадии готовности, не доказательство подписания.
- При несовместимых изменениях пользовательского поведения/API — версия с осознанным повышением major (после 1.0), при новых возможностях — minor, при совместимых исправлениях — patch. До 1.0 оговариваем несовместимые изменения особо.
- Версия формата проекта `.vcut`, версия протокола AI worker, версия самого worker и версий стороннего FFmpeg **независимы** от версии desktop-приложения: изменение номера приложения не должно мигрировать пользовательские файлы и не должно притворяться обновлением внутренних компонентов.
- `apps/desktop/package.json` — источник номера desktop. Синхронизируются `apps/desktop/package-lock.json`, `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/Cargo.toml`, `Cargo.lock` для `zeter-desktop-tauri`, `release/runtime-manifest.json` (только `app.version`). Версия в интерфейсе импортируется из package.json при сборке.
- Новый номер создают `node scripts/set-version.mjs 0.1.0-alpha.2 --note "подробное описание ..."`. Скрипт добавляет новый датированный раздел со статусом и первым содержательным изменением, обновляет манифесты/lockfiles. Затем записи по категориям вручную дополняют фактами. Без описания повышение запрещено.

## Структура журнала

```markdown
## [0.1.0-alpha.2] — 2026-10-12

> Предварительная версия (ещё не опубликована).

### Добавлено
- В таймлайне: ... Как включить ... Чем помогает ... (#123).

### Изменено
- ...

### Исправлено
- При ... происходило ... Теперь ... Тест ... (#124).

### Безопасность
- ...

### Документация
- ...
```

Категории по необходимости: `Добавлено`, `Изменено`, `Устарело`, `Удалено`, `Исправлено`, `Безопасность`, `Документация`. Не создавать пустых категорий и повторяющихся заголовков. Новые версии сверху, старые не переписывать без явного исправления фактической ошибки. Сохранять реальные даты в формате YYYY-MM-DD.

## Правила для каждого PR

1. До кодирования понять влияние на UI, экспорт, проекты, кэш, безопасность, производительность, упаковку и диагностику. Для всех значимых изменений добавить запись в `CHANGELOG.md` **в том же PR**. Писать по одному подробному пункту на самостоятельное изменение, а не «улучшения», «багфиксы», «рефакторинг».
2. Указывать конкретную поверхность и поведение до/после, ограничения, платформу, данные/миграции, ссылки на PR и тесты. Security-исправления описывать без опасных инструкций эксплуатации. Исправления чисто внутренних тестов тоже записывать, если они влияют на качество выпуска.
3. Если PR draft/stacked и не включён в `main`, не объявлять функцию в реальном релизе `main`. Предлагаемый пункт changelog попадёт в `main` только вместе с кодом, после merge. При конфликте версий переносить пункт в правильную актуальную секцию.
4. Изменили только детали в ранее подготовленном PR? Дополнить существующий пункт, сохранить факт проверки и ссылку. Не дублировать одно изменение как несколько опубликованных релизов.
5. Перед merge: `node scripts/check-version.mjs`, `npm --prefix apps/desktop run build`, `npm --prefix apps/desktop test -- --run`, `cargo fmt --all -- --check`, `cargo test --workspace`; Windows CI и ручные проверки по риску. Запуск теста не равен успешному прохождению.
6. После merge проверить, что в `main` присутствуют и изменение, и запись. При выпуске использовать `node scripts/release-notes.mjs <version> --output release-notes.md`, затем подписывать и публиковать только после утверждённого качества.

## Контроль качества

- `node scripts/check-version.mjs` завершится ошибкой, если версии программы расходятся, нет её раздела, секции пусты, нарушены номера, либо присутствует отдельный безверсийный заголовок. Проверяет также, что worker-version согласован со своей независимой manifest identity.
- `node scripts/check-version.mjs --tag v0.1.0-alpha.2` проверяет точное совпадение готовящегося тега с файлами. Тег не создаётся автоматически.
- `node scripts/release-notes.mjs 0.1.0-alpha.2 --output release-notes.md` формирует текст только из нужной секции; соседние версии в релизные заметки не попадают.
- CI запускает проверку до npm build. Release workflow повторяет её до публикации; реальные release secrets и подписи всё ещё обязательны.
- Отсутствие записей про неслившиеся ветки в опубликованном `main` — осознанное требование точности истории, а не потеря прогресса. Планы/незавершённые PR хранятся отдельно.

## Запреты

Не ставить новые теги, не публиковать релиз, не заменять установленную программу, не включать автообновление и не считать DEBUG-артефакт подписанным без отдельной приёмки.
